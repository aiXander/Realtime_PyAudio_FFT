# 3D FFT view: core + styles, and the UI palette

Map of how the 3D FFT card and the UI-wide color palette work. Read this before adding a style, changing the 3D core, or touching colors anywhere in `ui/`.

## Files

| File | Role |
|---|---|
| `ui/src/viz/fft_3d.js` | **Core.** History ring, display smoothing, mesh + vertex buffer, WebGL context (loss/restore), static layer (background, style art, axis labels), the GL overlay canvas, incremental mesh build, CPU + GPU perf recording. Knows nothing about looks. |
| `ui/src/viz/fft3d_styles/common.js` | The **style contract** (header comment), shared shader snippets (`PROJ_FN` projection, `SURF_VS`, `bandFn`, `RAMP_FN` magnitude colormap, `LINE_FN` AA grid lines, `LOG_PAPER_FN` log graph paper, `HASH_FN`, `FLAT_VS`), `program()`, `setCommonUniforms()`, front-edge strips (`fillCurtain` / `fillRim`), `drawSecondLabels()`, `disposeAll()`. |
| `ui/src/viz/fft3d_styles/index.js` | Registry: `STYLE_ORDER` (dropdown order), `STYLES`, `DEFAULT_STYLE`. |
| `ui/src/viz/fft3d_styles/<name>.js` | One module per look: `cloud` (the original, palette-colored dust), `topo` (survey map), `spectrogram`, `partials` (the detail-first ones, below). Look constants sit at the top of each. |
| `ui/src/colors.js` | **Palettes** + the mutable `LMH` / `LMH_HEX` / `theme` objects every viz reads. |
| `server/control/validate.py` | `FFT3D_STYLES` / `PALETTES` name lists — **keep in sync** with the registry and `PALETTE_ORDER`. |

## Selection and persistence

Both choices are server-authoritative UI settings, same pattern as the 2D/3D toggle: dropdown → WS `set_fft3d_style {style}` / `set_palette {palette}` → `cfg.ui.fft3d_style` / `cfg.ui.palette` (persisted in YAML) → meta `ui_fft3d_style` / `ui_palette` → `controls.syncMeta` sets `store.fft3d_style` and calls `applyPalette()`. The style dropdown sits in the FFT card title and only shows in 3D view. The palette dropdown is in the top bar. Unknown names in YAML fall back to the default (`_or_default` in `server/config.py`), so removing a style never breaks config loading.

## Style contract (short version, details in `common.js`)

A style default-exports `{ name, label, description, camera?, background, text?, drawStatic?, smoothing?, create(gl, f) }`. `create` returns `{ render(f), dispose() }`.

- **Only one instance is alive.** The core disposes the old instance on a switch, so an unused style holds no GPU memory. It also recreates the instance after a context restore.
- `f` is one preallocated bundle mutated per frame: geometry (`geo`), mesh (`meshH`, `meshZ`, `R`, `mc`, `surfVao`, `triCount`), front edge (`edgeX/edgeY`, `yBaseF`), band stops (palette), `t` (wall clock), `key0` / `tSub` (row keys). `render()` must not allocate.
- `camera: { backScale, ampFront }` reshapes the projection. The projection is a uniform (`uK`, `uBackScale`), not baked into shaders.
- `smoothing: { freqOct, timePasses }` lowers the core's display smoothing for this style (defaults: σ 0.08 oct across frequency, 2 peak-preserving time passes). The core keeps the *unsmoothed* history ring, so a switch re-smooths every stored row at once (`syncSmoothing` in `fft_3d.js`) and invalidates the incremental-mesh carry-over. The resolution floor (`FREQ_RES_SIGMA`, ≥ 0.6 rfft-bin spacings) always applies: below it there is no real detail, only the server's interpolation between rfft bins.
- Lines that must sit exactly on history rows use `vRow` from `SURF_VS` with `uRow0 = f.key0 % P` (P a power of two ≥ `tSub · 2^levels`): `vRow / tSub` is an integer on every history row and its parity is stable as rows recede, so "every 2nd / 4th row" thinning doesn't flicker. `vKey` wraps at 65536 and isn't safe for this. Lines on a uniform time grid instead use the absolute clock: `phase = (f.t · N / depthS) mod 1`, `line = phase − z·N`.

## Decisions and traps

- **Row timing:** `rowT` = the row's *slot close time* (first frame + one slot), fixed when the row opens. It used to be the latest merged frame's arrival, which made rows twitch backward on every merge. Invisible in `cloud`'s dust, but it read as stutter in the crisp-line styles. The open row has `z < 0 → 0` and is the live front edge (no "pin while fresh" hack any more).
- **Styles were pruned to the ones that show data (2026-10-23).** Aurora, synthwave, engraving and embers (bloom, particles, audio-reactive effects) were removed as gimmicky and low on detail, and later `waterfall` (hidden-line traces per row) because it looked bad; the bloom post-process, `heightTex` texture upload, `audio` / `bandU` / `dt` frame fields and the `camera.horizon` sky went with them. If an effect comes back, git history has them (commit before this change). The bar for a new style: it must show *more* of the data than cloud/topo, in one opaque pass, no post-processing.
- **The detail-first styles.** Both use `RAMP_FN`: a palette colormap with luminance forced to rise monotonically (like viridis/inferno), so magnitude reads correctly whatever the palette's own colors are.
  - `spectrogram`: shallow-perspective sheet (`backScale 0.72`, `ampFront 0.15`), log graph paper + 1 s parallels. Colormap input is `level = (h · 1.4)^0.85`. Measured 2026-10-23 (strength 0.8): non-zero bins have median ≈ 0.24, p90 ≈ 0.53, max ≈ 0.88, because `tanh · strength` rarely gets past 0.8. An earlier gamma 1.6 (based on the wrong belief that music sits in 0.5–0.9) put the median bin at ≈ 0.1 on the colormap, so the sheet looked flat and dark.
  - `partials`: peak tracking with no extra pass. A peak is where the interpolated frequency slope (`-vN.x`) crosses zero going down; the line is drawn at that crossing (`|sx| / |∇sx|` = px distance). Peak width is estimated as `σ ≈ √(h / −h'')`, so narrow tonal peaks light up and broad humps or small ripples on a high floor stay dark. The slope attribute is `0.25 · dh/du` (from `WORLD_HEIGHT` in `fft_3d.js`); change one, change `SLOPE_PER_DHDU` too.
- **Perf panel has an `fft_gpu` row** (WebGL timer query around `render()`). The `fft` row is CPU only and hid every fill-rate problem. Card size (≈ 760×340 CSS px @2×, M2, 2026-10-23): cloud ≈ 3.4 ms, topo ≈ 1.6, spectrogram ≈ 1.4, partials ≈ 1.7. Full screen, earlier: cloud ≈ 4.7, topo ≈ 4.0. These numbers double when another GPU app (e.g. DaVinci Resolve) is busy, so compare against cloud measured at the same time.
- **UI CPU / frame-rate traps (measured 2026-10-08, headed Chromium, M2, 1600×1000 @2×).**
  - *Compositing:* the GL canvas is a DOM overlay (`canvas.viz-overlay` in `.viz-stack`), not `drawImage`d into the 2D canvas. The per-frame copy stalled the GPU pipeline: 3D ran at ~35 fps, 2D at 60. The overlay is hidden (`showGl(false)`) whenever no GL frame is drawn (empty states, 2D view via `fft3d.hide()`), because a WebGL canvas keeps showing its last frame.
  - *Incremental mesh:* `buildMesh` carries over the vertex rows whose history-row dependencies (`timePasses + 2` back / `timePasses + 3` forward around their own row: time blur ±passes, Catmull-Rom −1..+2, slopes ±1) are all closed and not clamped at the back edge, shifting them by whole rows (`copyWithin`, keyed on `rowSeq`) and rewriting only `z`. Recomputed per frame: ~10 history rows at the front edge and the horizon. CPU per frame went ~2 ms → ~0.7 ms. Verified bit-identical heights against a full rebuild (vertex diff ≤ 2e-7). Any change that makes a closed row's content or z-spacing change over time (e.g. re-merging into old rows, a non-linear z) must also invalidate the carry-over (`finalMc = 0`). A depth, mesh-width or smoothing change already does.
  - *Shared canvas:* 2D and 3D each have their own `makeSurface` on the same canvas, so `fit()` also compares against its own `s.w/s.h`. Otherwise the view that didn't do the resize draws at a stale size after full screen / tiling changes.
  - *Perf panel:* the bars animate `transform: scaleX`, not `width`, and `.perf-num` is a fixed box with `contain: strict`. A `width` transition re-laid-out the whole side panel on every frame it ran (5 Hz status × 11 rows): ~70 ms/s of layout + paint on the main thread, in both views.
- Crisp lines use `fwidth`-based AA and fade where they crowd (`lineAt` in topo, `gridLine` / `LOG_PAPER_FN` in common). Otherwise the far rows moiré.

## Palette

`applyPalette(name)` mutates `LMH` / `LMH_HEX` / `theme` in place, bumps `theme.version`, and sets CSS custom properties on `:root` (`--low/--mid/--high`, `--accent*`, `--bg-*`). DOM and CSS follow automatically: `freq_axis.js` uses inline `var(--low)` styles, and the brand logo does the same. Canvas viz that cache colors key their caches on `theme.version`: `lmh_bars` flash ramp, `lmh_lines` gradients, `lmh_scene` sprites/fills, `fft_2d` bucket ramp + band overlays, the 3D static layer and band stops. A palette sets the band colors, accent, background tint and the 2D spectrum ramp (`ramp: null` = the original formula). The palette also drives **every 3D style**. Shaders read `uC0/uC1/uC2` (low/mid/high, declared via `PAL_UNIFORMS`, set by `setCommonUniforms`). Static art uses `pal()` / `palBg()` from `common.js`. Each style maps its roles onto the palette: cloud = band colors across frequency; topo sea = low, lowland = mid, highland = high; spectrogram / partials = `ramp()` (hue low → mid → high, lightness-ordered). A style's `background()` is re-read only when the style or palette changes (`theme.version`), never per frame. The top-bar picker is a custom listbox (`setupPalettePicker` in `controls.js`) because a native `<select>` can't show swatches. The scene viz caps saturation at the palette color's own, so `mono` stays grey.
