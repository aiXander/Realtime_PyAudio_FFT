# 3D FFT view: spectro stream, core, styles, and the UI palette

Map of the 3D FFT card and the UI-wide color palette. Read this before adding a style, changing the 3D core or the spectro stream, or touching colors anywhere in `ui/`.

The 3D view does **not** show the LED-oriented FFT the 2D view shows (`/audio/fft`, smeared, smoothed and autoscaled per bin). It has its own analysis made for looking, the **spectro stream**: a multi-resolution STFT on the server (a frame every ~5 ms, 1024 log bins 20 Hz–20 kHz, raw dB), sent only to clients that ask for it (`set_spectro`). The stream is raw: no smoothing on the server. The UI averages each frame in power over the last ~40 ms and over ~1/6 octave, keeps the history in one GPU texture, and every pixel of every style reads that texture directly. The **source** radio (`ui.fft3d.source`) can instead feed it the `/audio/fft` frames the 2D view draws: see [Source: the OSC stream](#source-the-osc-stream).

**What the view is for:** watching music and recognising what you hear. The three things that decide that, in order: the picture must not lag the sound, quiet content must not stand as tall as loud content, and detail finer than hearing must not be drawn. See "Why it reads as the music" below before changing the analysis timing, the height mapping or the integration.

## The spectro analysis (server)

- **Window ladder.** Every hop runs Hann windows of 512 … 8192 samples (at 44.1–48 kHz; the ladder scales with sr), zero-padded 2×, that all **peak at the same instant, ~21 ms behind the newest sample** (half of the third window). Windows up to 2048 are plain Hanns centred there; 4096 and 8192 can't be centred that late, so they are lopsided: a long half-Hann rise, a 1024-sample half-Hann fall ending at the newest sample (`ladder_window` in `spectro.py`, `Spectro::new` in `spectro.rs`). Pinned by `a_fresh_onset_already_shows` in `spectro.rs`.
- **Per log bin**, the wanted window is `sr / (f · rel_res)` (constant Q), clamped to the ladder; the bin crossfades in dB between the two nearest windows, so there are no seams. A log bin wider than a padded rfft bin takes the **max** of the bins it covers (tonal peaks survive); a narrower one interpolates.
- **Amplitude-normalised** (a sine reads its dBFS level in any window). With constant-Q windows, pink noise then reads flat between the clamps; the ladder is clamped above ~2 kHz, so treble falls off and the UI's default tilt is +3 dB/oct.
- **`res`** picks `rel_res`: `time` 0.08, `balanced` 0.045, `pitch` 0.02. Hann's main lobe is ~2.5 bins, so `pitch` splits a semitone above ~200 Hz (pinned by `resolves_a_semitone_at_440` in `spectro.rs`). One analysis serves every subscriber; the last request wins.
- **Hop** = the whole number of blocks nearest 5 ms (256 samples at 48 kHz / 256-block).
- **Cost** (M2, live): Rust ≈ 0.1–0.3 ms per hop (2–5 % of a core); Python ≈ 1 ms per hop (~20 %, mostly GIL contention), no dropped blocks. Only while a 3D view is subscribed; the thread idles otherwise.
- **Not realtime; the analysis is parity-tested, the service isn't.** `Spectro` (the per-frame analysis) has a DSP golden in both engines ([`dual_engine.md`](dual_engine.md)); the worker loop, `set_spectro` and the binary wire don't. The worker polls the slot ring every 4 ms at normal priority (the ring keeps ≥ 2 × 16384 samples), so the callback doesn't know it exists and the LED path (DSP, FFT, OSC, goldens) is untouched. It is deliberately outside `server_status` and `meta` (their key shapes are compared by the wire-parity tool); its cost goes out as a separate `spectro_perf` message.

## Why it reads as the music

Measured on house music, before these three were in place the view looked like noise and felt detached from the sound (the 2D view, which has all three by construction, felt in sync):

- **Latency.** With every window centred on the middle of the longest one, the stream reached the browser 75–85 ms after the L/M/H snapshot of the same hit; the playhead and the integration add ~30 ms. A picture that trails the sound by > ~45 ms is seen as late. With the windows peaking 21 ms back it is ~15 ms (mid, treble) and ~20 ms (64–160 Hz). A centred Hann would leave the bass at ~50 ms: that is what the lopsided long windows buy, for wider skirts (−20 dB at ±2.8 rfft bins instead of ±1.7; the −6 dB width is unchanged). Don't re-centre the ladder to tidy the alignment.
- **Height curve (`gamma`, the Curve picker).** Height = (dB-linear 0..1)^gamma, applied in `specH` and its CPU twin `levelAt`. At gamma 1 a sound 20 dB under the top (heard about a quarter as loud) stands half as tall on a 40 dB range, so every layer looks equally present and the ridges occlude each other. Default 2. `specDb` is the dB-linear read.
- **Frequency blur (`blur_oct`, the Detail picker).** The integrator blurs the power across frequency with a Gaussian of that full width at half maximum, default 1/6 octave. Above ~2 kHz the bins are ~1/100 octave and hearing pools about a third of an octave, so bin-level detail there is a field of spikes with nothing audible behind it. It is a mean, so a flat spectrum keeps its level and a lone narrow line drops (−11 dB at 1/6 octave for a 3-bin line): noise and tones are then both shown as power per band. The bass is untouched (its analysis is already coarser). ~0.03 ms per frame.
- **Tonal emphasis (`tonal`, the Tonal picker).** Height is energy, and a melody sits 15–25 dB under the drums; the ear follows it because it is narrow in frequency and steady in time. The integrator measures that per bin (power blurred 1/24 octave against the box mean of the half octave around it, 3 → 8 dB = 0 → 1, 50 ms to rise so a hit doesn't count) and writes it as the texture's second channel (the ring is RG8: level, tonalness). The display mapping lifts tonal bins toward the top (`toneLift` in `fft3d_data.js`, GLSL twin in `specDb`): nothing at the floor, nothing at the top. The lift is in the mapping, not in the stored dB: lifted data raised the auto level and pushed everything else down. Synthetic check: noise reads 0, a 14 dB tone 255, a broadband hit ~3.
- **One visual vocabulary for the kind of sound, shared by every style.** A **note is a white thread along time** (`specThread`: a line on the crest of a clearly tonal ridge, as long as the note sounds); a **beginning is lit across frequency** (`specOnset`: the level rose ≥ 4 dB in the last 30 ms, so a hit is a streak and a note gets a dot at its head). White is reserved for notes: `spectrogram` stops its colormap short of white for that reason. Keep the mark the same in a new style, so what is learned in one view carries to the next.
- **Color by moment (`moment`, the Color picker; 0 = the style's own colors).** A style's own hue repeats what the picture already says (cloud: place on the frequency axis; spectrogram: level). By moment, a whole row takes the hue of the bands sounding in that frame (palette low / mid / high, mixed), so a kick, a snare and a hat differ in color across the row and rhythm reads as a color pattern along time. The idea is dadaspec's (the 3-band tinted spectrogram in `~/Documents/GitHub/AI_Audio`, `sa3lab/hispec.py`), adapted for a live stream: `makeMoment` writes one RGBA texel per row (a second texture, unit 1, `uRowTint`), `MOMENT_FN` in `common.js` turns it into the hue, and `momentMix` swaps a style's hue for it while keeping the style's brightness. Three things differ from dadaspec, each for a measured reason:
  - *Activity is the band's position between its own recent trough and peak*, not its level under a whole-clip maximum (there is no whole clip). A fixed range under the peak failed on real tracks: a held sub moves ~5 dB between kicks and hats ~20 dB between hits, so one range leaves the first always on or gates the second.
  - *What the three bands have in common is left out of the hue* (`MOMENT_COMMON`). In a dense mix all three are active and the plain sum is grey; without this the view was pastel throughout.
  - *The bands split where the user's L/M/H bandpass edges meet* (geometric mean of adjacent edges), so the colors agree with the other cards.
  It is baked per row when the frame arrives, so the picker re-maps the whole history but a band-edge change only affects new rows. The hue taps go back in time only (rows past the newest are stale).
- **"Now" is the front edge, and it has to win the eye.** The picture is 99 % past, in constant scroll. `cloud` lights the newest rows (`LIVE_GAIN`, dying off over `LIVE_TAU_S`) and draws a rim and filled curtain at the front, white where a note is sounding, so a hit flashes there before it recedes. `spectrogram` is flat, so it stands the live spectrum up as a curve at the front (`setEdgeAmp`). A new style needs its own answer to this.

## The UI core

- **Integration (`makeIntegrator`).** Each frame entering the ring is the power average of the last N raw frames per bin (a boxcar; the **Smooth** picker: raw / 20 / 40 / 80 ms, default 40), then blurred across frequency (above). This is Welch averaging: a tone keeps its level, noise-like content stops being a new random draw every 5 ms. It is in the UI, not the server, because it is display taste: the pickers change it live, both engines stay untouched, and a uniform boxcar adds nothing visible to the bass (its windows are already 85–170 ms).
- **History = one RG8 texture** (level, tonalness), `n_bins` wide, `TEX_ROWS` (8192) tall, used as a ring (row = seq mod 8192, REPEAT wrap, so any float row samples correctly, negative ones too). Each draw uploads only the rows that arrived. The dB → height mapping (range, tilt, level) is uniforms: changing it re-maps the whole history at once.
- **Level (`makeLevel`):** the dB mapped to full height is the loudest bin of the last 20 s plus 3 dB, approached with a 2 s rise and a 4 s fall, never below −50 dBFS. The rise is slow on purpose: a fast one squashed the whole picture at once when one loud hit landed. What is louder than the top meanwhile stands at full height (clipped); only a level more than 10 dB over the top (music after silence) is closed at once, down to that lag. Steady music keeps hitting the same peak, so the mapping stands still; a quiet passage shorter than 20 s stays low (it shows relative level).
- **Playhead (`makePlayhead`):** frames arrive in bursts (one message per broadcast tick). The largest "seq − arrival time" seen is the stream's clock; how far that clock had run past the newest held frame at each arrival is the lead the playhead needs. It advances by wall-clock time alone and trails the clock by the largest recent need, so its speed is constant. It never passes the newest frame, and snaps when more than 0.4 s off (reconnect, tab return). `draw(now)` takes the animation-frame timestamp.
- **Geometry vs. shading.** The grid (default 512 × 256 vertices; a style may set `grid`) only carries the relief: the vertex shader reads heights from the texture, pooling the data rows each grid row stands for. Grid rows are **anchored** to data rows (`step` whole rows apart) and glide with the playhead, plus one live front row at the playhead; sampling at moving positions instead made the surface crawl. Fragment shaders call `specSurface` (in `SPEC_FS`), which reads height and normal per pixel, pooled over the rows / bins under the pixel (`fwidth`), so detail is at data resolution. Pooling is halfway between mean and max of the taps (`poolMix`).
- **Subscription:** `syncSpectro` subscribes while connected, synced, in 3D view on source `spectro`, FFT enabled and the tab visible. The FFT enable toggle stays the one "off" switch. The server forgets subscriptions on disconnect, so `spectroSent` resets then.

## Source: the OSC stream

`source: fft` (the **OSC** radio) draws the `/audio/fft` frames the UI already receives for the 2D view, so the history is the 2D picture over time, i.e. what the LEDs got; the side-panel knobs shape it, the spectro stream is unsubscribed. `makeFftRows` turns each WS frame into one row holding exactly the 2D graph's height (processed: the value clamped to 0..1; raw dB: `(dB − db_floor) / span`, sentinels at 0), as `h·255` with `linear: true`. Linear rows pass the integrator untouched (one row, no blur, no tonal) and map with floor 0, range 1, no tilt, curve 1, so the Smooth / Detail / Range / Curve / Tonal / view-tilt pickers and Resolution hide; raw dB and the bin count show. Color by moment still works: the row carries a q → dB table (`qDb`) for `makeMoment`.

- **The row period is the WS tick, not the FFT hop.** The broadcast loop sends the latest FFT frame per tick, so a hop that lands between two ticks never reaches the UI. Period = `max(1 / ws_snapshot_hz, fft_hop / sr)`; that is why `meta` carries `fft_hop`. A wrong period makes the playhead outrun the data and stall.
- **Rows carry a local counter, not a server seq** (the type-1 frame has none). No frame for > 0.25 s becomes a gap of the elapsed rows, so a pause shows as one instead of being stitched shut.
- **History restarts** on a change of source, raw dB, the dB floor / ceiling, bin count or UI refresh rate (each changes the encoding or the period: `push` reconfigures).

## Selection and persistence

Both choices are server-authoritative UI settings, same pattern as the 2D/3D toggle: dropdown → WS `set_fft3d_style {style}` / `set_palette {palette}` → `cfg.ui.fft3d_style` / `cfg.ui.palette` (persisted in YAML) → meta `ui_fft3d_style` / `ui_palette` → `controls.syncMeta` sets `store.fft3d_style` and calls `applyPalette()`. The style dropdown sits in the FFT card title and only shows in 3D view. The palette dropdown is in the top bar. Unknown names in YAML fall back to the default (`_or_default` in `server/config.py`), so removing a style never breaks config loading.

The 3D view's own settings are server-authoritative too, in one block: `ui.fft3d` (pickers: `source`, `res`, `smooth_ms`, `blur_oct`, `range_db`, `gamma`, `tonal`, `moment`, `tilt_db_per_oct`; camera panel: `glow`, `bloom` (its Light sliders, read by `cloud` only), `overscan`, `perspective`, `skew`, `height`, `horizon`), set with a partial `set_fft3d {key: value…, commit?}`, mirrored from meta `ui_fft3d` into `store.fft3d`. Ranges: `FFT3D_RANGES` in both `validate` modules; a bad key in YAML keeps its default. Resolution is a `set_spectro` field; smooth and blur apply to frames from then on; the rest are uniforms. Adding a key means both `validate` tables, both config structs, every file in `configs/`, and re-recording `testdata/golden/wire/` (`uv run tools/parity/record_wire.py`): two Rust config tests compare against the captured YAML. Camera sliders also write `store.fft3d` while dragged (local preview) and ignore meta echoes while held (`bindSlider().held`).

## Style contract (short version, details in `common.js`)

A style default-exports `{ name, label, description, camera?, grid?, background, text?, drawStatic?, create(gl, f) }`. `create` returns `{ render(f), dispose() }`.

- **Only one instance is alive.** The core disposes the old instance on a switch, and recreates it after a context restore.
- `f` is one preallocated bundle mutated per frame: geometry (`geo`), grid (`R` rows, `mc` cols, `surfVao`, `triCount`, `rowDz`), front edge (`frontH`, `edgeX/edgeY`, `yBaseF`), band stops (palette), `t` (wall clock), and `spec` (every texture/grid uniform, set by `setCommonUniforms`). The texture is bound on unit 0 before `render()`. `render()` must not allocate.
- The grid VAO has **no attributes**: vertex shaders work from `gl_VertexID` through `gridVertex()` (u, texture row, z, row key, pool). `SURF_VS` outputs `vU, vH, vZ, vKey, vS, vT, vPx`; `vT` is the texture row to pass to `specSurface` / `specH`.
- `camera: { backScale, ampFront }` is the style's look at the camera panel's **perspective ×1 / height ×1**; the user's settings multiply it (`geometry()` in `fft_3d.js`), so per-style tuning survives one global camera.
- `specSurface` and `specThread` use `fwidth`, so they live in `SPEC_FS` (fragment only). Including them in a vertex shader fails to compile ("no matching overloaded function"). `specOnset` and `specTone` work in both stages (cloud's dust reads them per point).
- `SPEC_FN` declares `uDepthS` (the onset look-back is in seconds). A style that declares it again in the same shader fails to compile; a shader without `SPEC_FN` (cloud's point fragment stage) declares its own.
- Lines on a uniform time grid use the depth: `gridLine(vZ · depthS)` (1 s parallels).

## Decisions and traps

- **Projection (`PROJ_FN` + its CPU twin `projectRow` in `common.js`).** A row at depth z scales by s = 1/(1 + K·z) and sits `ground(z) = z(1+K)/(1+K·z)` of the way from the front baseline to the horizon; skew shifts it sideways by the same share. This form stays finite at K = 0 (perspective ×0, parallel rows). Depth is written from `ground(z)`, not from s: with s ≡ 1 at K = 0 every row would get the same depth and the back-to-front draw would let far rows paint over near ones. Overscan widens the front row past the card (`geo.halfW`), so the narrowing rows fill the width from a moment back instead of leaving empty corners; the x-axis labels follow `halfW` and drop ticks pushed off the card.
- **Never draw the raw frames.** A short-window bin of noise-like sound is chi-square distributed (~±5 dB) and independent from one 5 ms frame to the next above ~2 kHz. Drawn raw it is speckle, a front edge that dances at the display rate, and shimmer as the picture scrolls (each pixel's taps slide over uncorrelated rows). Max-pooling raw rows made it worse: the max of six random draws is biased ~4 dB up and still random. Measured on a music file (40 ms vs raw): treble frame-to-frame change 3.2 → 0.5 dB, scroll shimmer down 3–8×, largest treble onset rise in 21 ms 40 → 34 dB.
- **A boxcar, not a one-pole, for the integration.** A one-pole in power rises fast but falls only 4.3 dB per time constant: 25 ms leaves a ~350 ms tail behind every click on a 60 dB scale.
- **The level must not follow single peaks.** The mapping is one uniform for the whole history, so every change re-maps everything on screen. An instant-attack / 6 dB/s-release top moved ~9 dB/s in steady music: the floor dropped on every kick and crept back. Any new scheme has to hold still for material that keeps its level.
- **The playhead must not read past the newest row.** Rows beyond it hold data from 8192 frames ago; with linear filtering even row `lastSeq + 0.9` is mostly stale.
- **Shaders can be compiled without a browser:** build each style against a fake `gl` that records `shaderSource`, swap `#version 300 es` for `310 es`, run `glslc --target-env=opengl`. The data module runs in node as is.
- **Styles were pruned to the ones that show data (2026-10-23).** Aurora, synthwave, engraving and embers (bloom, particles, audio-reactive effects) were removed as gimmicky and low on detail, later `waterfall` (hidden-line traces per row) because it looked bad, and `partials` (a line traced along every spectral peak) because the lines read as clutter, not as notes (`specThread` is the same idea gated hard on tonalness, a few lines instead of dozens; don't loosen its gate: on half-tonal swells the crest wanders and the line reads as a crack); a core-level bloom post-process, `heightTex` texture upload, `audio` / `bandU` / `dt` frame fields and the `camera.horizon` sky went with them. If an effect comes back, git history has them (commit before this change). The bar for a new style: it must show *more* of the data than cloud/topo, in one opaque pass, no post-processing.
- **Cloud's light is two dials, and bloom is back there by Xander's choice.** `glow` mixes two ways of lighting the same opaque surface (0 = matte terrain under a key light, 1 = a dark body that emits by level); `bloom` is the gain of a pass owned by `cloud.js` (the bright parts drawn again into a quarter-resolution target, blurred, added on top), skipped entirely at 0. The translucent surface it replaces (alpha 0.5, colors faded 30 % toward grey) read as brown mud: overlapping ridges blended instead of hiding each other. The bloom sources are not multiplied by the front-edge light, or the front burns out to white.
- **Each style has a job; a relief with different paint is not one.** `topo` and `spectrogram` used to be the same relief as `cloud` under a tint and a colormap, and read as near-duplicates. `spectrogram` is now flat and seen from above (`ampFront` ≈ 0, little perspective), colored by dB-linear level whatever the Curve picker says: no ridge hides another, so rhythm and note sequences read as evenly spaced marks, like a piano roll. `topo` is still a relief; its only own content is the contour lines.
- **The thread's crest is found over ±0.06 octave, not ±1 bin.** With the default 1/6-octave blur a peak falls under 0.1 dB one bin from its top, below the texture's 0.5 dB steps, so a narrow baseline finds nothing or jitters.
- **Cloud's dust is data.** The points sit on jittered grid vertices (the jitter and a per-point random brightness are polish). They are a faint grain scaled by height everywhere and bright only on tonal ridges and onsets. Before that they were bright wherever the surface was high and added nothing the surface didn't show.
- **`spectrogram`** uses `RAMP_FN`: a palette colormap with luminance forced to rise monotonically (like viridis/inferno), so magnitude reads correctly whatever the palette's own colors are. Height is dB-linear over the display range, so it needs no gain.
- **Perf panel:** an `fft_gpu` row (WebGL timer query around `render()`; the `fft` row is CPU only and hides fill-rate cost) and a `spectro` row (server worker, from `spectro_perf`). Card size (≈ 715×232 CSS px @2×, M2, house music): cloud with bloom 1 ≈ 5.4 ms GPU median (surface ≈ 3.6 incl. 0.6 pre-pass, dust ≈ 1.3–1.6, bloom ≈ 0.9, front edge ≈ 0.2); spectrogram ≈ 4.5. Filling a 1389×779 window (older numbers): topo ≈ 6.5, spectrogram ≈ 5.9.
- **What the GPU time goes to: triangle count and hidden fragments, not texture reads.** The grid's triangles are a few px at the front and sub-pixel toward the horizon and at bloom's quarter resolution, and a GPU shades at least a 2×2 quad per triangle. So: (1) cloud's surface blends, which stops the GPU from skipping hidden fragments, so it lays down depth first (`DEPTH_FS`, `invariant gl_Position` in `SURF_VS`), −1 to −2 ms; (2) the bloom pass draws every 3rd grid row and column (`makeCoarseGrid`; color is still per pixel), 2.3 → 0.9 ms. Any thinned grid must pick rows by **row key**, not index (one index buffer per phase): every 3rd row by index lands on different data rows at each grid step, and the bloom flickered white over the whole picture. A coarser *main* grid halves the surface pass but visibly blurs the ridges (rejected); a 1024 × 480 grid cost twice the default with no visible gain. Skipping dust points on the floor saved nothing measurable (rejected). topo / spectrogram are opaque without blending, so the GPU already skips their hidden fragments.
- **Measuring `fft_gpu`: compare medians from an interleaved A/B, never two runs.** The mean and the peak are inflated by GPU contention (spikes of +7–10 ms show even when only the two front-edge strips are drawn) and the load follows the music, so runs a few seconds apart differ by more than most changes. Toggle the variants every ~250 ms within one 15–30 s window, reading `store.viz_perf.fft_gpu` (`import('/src/store.js')` from the page). Numbers double when another GPU app is busy.
- **UI frame-rate traps.**
  - *Compositing:* the GL canvas is a DOM overlay (`canvas.viz-overlay` in `.viz-stack`), not `drawImage`d into the 2D canvas. The per-frame copy stalled the GPU pipeline: 3D ran at ~35 fps, 2D at 60. The overlay is hidden (`showGl(false)`) whenever no GL frame is drawn (empty states, 2D view via `fft3d.hide()`), because a WebGL canvas keeps showing its last frame.
  - *Shared canvas:* 2D and 3D each have their own `makeSurface` on the same canvas, so `fit()` also compares against its own `s.w/s.h`. Otherwise the view that didn't do the resize draws at a stale size after full screen / tiling changes.
  - *Perf panel:* the bars animate `transform: scaleX`, not `width`, and `.perf-num` is a fixed box with `contain: strict`. A `width` transition re-laid-out the whole side panel on every frame it ran (5 Hz status × 11 rows): ~70 ms/s of layout + paint on the main thread, in both views.

## Palette

`applyPalette(name)` mutates `LMH` / `LMH_HEX` / `theme` in place, bumps `theme.version`, and sets CSS custom properties on `:root` (`--low/--mid/--high`, `--accent*`, `--bg-*`). DOM and CSS follow automatically: `freq_axis.js` uses inline `var(--low)` styles, and the brand logo does the same. Canvas viz that cache colors key their caches on `theme.version`: `lmh_bars` flash ramp, `lmh_lines` gradients, `lmh_scene` sprites/fills, `fft_2d` bucket ramp + band overlays, the 3D static layer and band stops. A palette sets the band colors, accent, background tint and the 2D spectrum ramp (`ramp: null` = the original formula). The palette also drives **every 3D style**. Shaders read `uC0/uC1/uC2` (low/mid/high, declared via `PAL_UNIFORMS`, set by `setCommonUniforms`). Static art uses `pal()` / `palBg()` from `common.js`. Each style maps its roles onto the palette: cloud = band colors across frequency; topo sea = low, lowland = mid, highland = high; spectrogram = `ramp()` (hue low → mid → high, lightness-ordered). A style's `background()` is re-read only when the style or palette changes (`theme.version`), never per frame. The top-bar picker is a custom listbox (`setupPalettePicker` in `controls.js`) because a native `<select>` can't show swatches. The scene viz caps saturation at the palette color's own, so `mono` stays grey.
